# CLAUDE.md

Guidance for AI assistants working in this repository.

## Repository overview

This repo contains **two unrelated projects**. Do not mix them, share code
between them, or "refactor" one to resemble the other.

1. **Forja Work benchmark harness** (`forja/`, `tests/`, `EDGE.md`,
   `HYPOTHESIS_V2.md`, `BENCHMARK.md`, `RED_TEAM_V2.md`) — the active focus.
   Benchmark V2 tests whether Forja beats a competent production-grade AI
   baseline on measured human work. Python 3.11, stdlib only (`anthropic`
   SDK optional for live mode; `pytest` for tests).
2. **CEX microstructure recorder** (`cex_microstructure_mvd/`) — a frozen,
   self-contained deployment artifact that records public crypto market data
   on a VPS. Touch it only when explicitly asked.

There is no CI configured. Run tests locally before every push.

## Read this first — frozen documents

- **`EDGE.md` is frozen. Never edit it.**
- **`HYPOTHESIS_V2.md` is frozen.** It pre-registers the V2 verdict:
  thresholds, metric definitions, non-inferiority margins, statistical bar,
  and the BUILD/PIVOT/KILL mapping. **Do not change thresholds or
  definitions after seeing results — ever.** If a definition proves broken,
  say so to the founder; do not patch it.
- **`BENCHMARK.md`** is the living methodology document; **`RED_TEAM_V2.md`**
  is generated by `python3 -m forja.bench.report` — regenerate it, don't
  hand-edit it.
- V1's offline headline numbers are invalid for product decisions. Do not
  quote them as evidence of an edge.

## Forja Work

### Commands

```bash
python3 -m pytest tests/ -q                                  # 116 tests, offline, fast
python3 -m forja.bench.corpusgen.generator --size 10000      # regenerate benchmark_data/
python3 -m forja.bench.run_v2 --mode offline --slice 1000    # phase 1: run arms (NO gold)
python3 -m forja.bench.score_v2 runs_v2/<run_id>             # phase 2: score vs gold
python3 -m forja.bench.adversarial                           # hostile-case suite
python3 -m forja.bench.review start --run runs_v2/<id> --reviewer <name>   # measure HAM
python3 -m forja.bench.labeling export --run runs_v2/<id> --out labeling_batches/b1
python3 -m forja.bench.report --results ... --adversarial ...  # regenerate RED_TEAM_V2.md
python3 -m forja.bench.run_v2 --mode live --slice 1000       # THE experiment (needs creds)
python3 -m forja.run_benchmark --mode offline                # V1 harness (superseded)
```

Live mode uses the official `anthropic` SDK, zero-arg client; default model
`claude-opus-5` for every arm (override with `FORJA_MODEL`). Generated data
(`benchmark_data/`) and run artifacts (`runs/`, `runs_v2/`,
`review_sessions/`, `labeling_batches/`) are git-ignored; the corpus
regenerates byte-identically from its seed.

### Architecture

```
forja/
  taxonomy.py         vocabularies: skills/aliases, transfer map, CEFR, licenses,
                      certifications registry, city/commute table
  schemas.py          Candidate/Job/Certification; strict validation; BENCHMARK_TODAY;
                      job structured fields = imperfect PARSE of the ad (V2)
  textutil.py, runlog.py, llm.py (THE LLM BOUNDARY: Anthropic + offline stand-in)
  baseline.py         V1 baseline + shared candidate/job render used by all V2 prompts
  pipeline/           the Forja spine: profiling → constraints (SOLE AUTHORITY, 12
                      dimensions) → retrieval → matching (evidence) → softpref
                      (bounded LLM, quote-gated) → gaps → recommend (FINAL GATE)
  workflows/          V2 arms b0/b1/b2/b3 + common.py (schemas, chunking,
                      claim_supported). MUST NEVER import gold (AST-tested).
  bench/              V2 infrastructure:
    corpusgen/        generator (families, archetypes) → jobs_v2.json + manifest.json
    goldgen.py        manifest → grades + truth-judged violations (EVAL SIDE ONLY)
    run_v2.py         phase 1 (no gold imports)   score_v2.py  phase 2 (gold)
    review.py+events.py  blinded review console; HAM = the primary metric
    labeling.py       blind human labeling, agreement, gold validation
    adversarial.py    hostile cases   costs.py  pricing   report.py  RED_TEAM_V2.md
  evaluation/         V1 evaluator (kept for the V1 suite)
  data/               candidates.json (10) + candidates_v2.json (14) + V1 jobs/labels
```

**Dependency rules (enforced by tests/test_v2_leakage.py — keep them green):**

1. Deterministic modules never import `llm.py`; inside `pipeline/` only
   `profiling.py`, `softpref.py`, and the orchestrator may touch the model.
2. `forja/workflows/*` and `forja/bench/run_v2.py` never import the gold side
   (`goldgen`, `corpusgen`, `labeling`, manifest/label files). Matching and
   scoring are separate programs.
3. `pipeline/` never imports `bench/` or `evaluation/`.

### Non-negotiable invariants

1. **Hard constraints are never overridden by an LLM.** `pipeline/constraints.py`
   decides eligibility; the filter runs before ranking AND `recommend.py`
   re-checks at emission. The soft-preference stage adjusts ranking only,
   with capped weight, and only for quotes verbatim in the candidate's text.
2. **Every recommendation carries machine-checkable claims** (verbatim quotes
   into the records); the scorer verifies every claim identically for every
   arm. Only *valid* certifications satisfy requirements — expired/pending
   never do.
3. **No optimization against benchmark answers.** Never tune weights,
   thresholds, prompts, or the corpus against per-pair results or gold
   labels. Aggregate structural findings (e.g., "text-only constraints defeat
   the deterministic spine") go into RED_TEAM_V2.md as findings; arm changes
   wait until after the live run and apply to the comparison fairly (if B3
   gains a text-verification stage, B2's spec question must be revisited —
   see red-team Q5). Gold changes only via the generator + documented rubric
   change, never per-example.
4. **Log everything**: model calls in full (`model_calls.jsonl`, tagged with
   workflow + candidate for cost attribution) and every pipeline/arm decision
   (`decisions.jsonl`).
5. **Determinism**: generator, offline arms, retrieval, scoring — all seeded/
   stable-sorted; `BENCHMARK_TODAY` instead of wall-clock in logic.
6. **Scope guardrails**: no UI, auth, billing, CRM, or sales infrastructure.
   The review console is a measurement instrument, not a product.
7. **Honest reporting**: offline runs are harness validation and must carry
   the offline warning; HAM is "NOT MEASURED" until real review sessions
   exist; RED_TEAM_V2.md never answers beyond the evidence. If B2 ≈ B3 in the
   live run, the report says the architecture has no demonstrated edge —
   sunk cost is never an argument.

### Dataset conventions

- Candidate structured fields are ground truth about the person; ambiguity
  lives in `free_text`/`constraint_notes`. Certifications carry status
  (`valid`/`expired`/`pending`).
- Job structured fields are a *parse* of the ad (`structured_completeness`);
  the description text is authoritative. Empty `shifts` = unstated (engine
  flags unverified). Salaries are 100%-equivalents. Job skill strings are
  free text (not taxonomy-bound); candidate skills are taxonomy ids.
- Corpus edits happen in `bench/corpusgen/` (families/archetypes/generator) —
  never by hand-editing generated files. After any change: regenerate, run
  `tests/test_v2_corpus.py`, and expect the checksum to change (note it in
  the commit message).
- V1 data files (`jobs.json`, `labels.json`) stay frozen with the V1 suite.

### Testing expectations

116 tests. New arm/pipeline capability ⇒ unit test + determinism check +
proof that structured-visible constraint violations still cannot escape.
Leakage tests are release blockers. Adversarial suite must show zero FAIL
offline.

## CEX microstructure recorder (`cex_microstructure_mvd/`)

Persistent recorder for public OKX + Coinbase market data into partitioned
parquet via systemd, with daily quality reports. See
`cex_microstructure_mvd/README_DEPLOY.md`. Hard guardrails (by design — do
not "fix"): public data only, no API keys, no auth, no orders, no trading,
no backtests, no secrets. Validate changes with
`scripts/daily_quality_report.py --date all` (expect `VERDICT: PASS`); no
automated test suite.

## Standing rule — always deliver the result documents

**After every task, hand the founder the current result documents as files**
(via the file-sending mechanism, not just as prose in chat). This is a
standing instruction, not a per-task request.

Always include:

| File | What it is |
|---|---|
| `REAL_WORLD_NAV_VALIDATION.md` | latest real-world (NAV) validation result |
| `RED_TEAM_V2.md` | the frozen Benchmark V2 verdict (B3 → KILL) |
| `MATCH_ENGINE_V1.md` | the frozen matching architecture decision |

Add whatever other artifact the task produced (e.g. a new benchmark summary,
a labelling batch manifest). If a task changed none of them, still send the
unchanged current versions and say plainly that nothing changed — the
founder wants the current state in hand after every assignment, not a diff.

Keep these documents regenerated/up to date before sending: `RED_TEAM_V2.md`
comes from `python3 -m forja.bench.report`; never hand-edit it.

## Git conventions

- Work on `claude/`-prefixed branches; push with `git push -u origin <branch>`;
  never push `main` directly.
- Full test suite before every push. Never commit `runs/`, `runs_v2/`,
  `benchmark_data/`, `review_sessions/`, `labeling_batches/`, `__pycache__/`,
  or credentials.
- Commit messages: imperative summary; matching/scoring/corpus changes need
  the domain justification required by invariant 3.
